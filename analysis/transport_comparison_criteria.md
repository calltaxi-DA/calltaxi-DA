# 이동수단 비교 분석 기준

상태: 확정 (2026-09-12)
목적: 장애인 콜택시·지하철·저상버스를 같은 단위로 비교할 핵심 지표를 확정하고, Backend Phase 7 추천 정렬에 전달할 입력과 분석 참고용 결과를 분리한다.

## 이번 Phase 범위

이번 문서는 **Analysis Phase 7** 산출물이다. 기존 분석 문서와 서비스가 현재 생성할 수 있는 경로 결과를 확인해 비교 기준을 정의한다. 원본·전처리 데이터를 재생성하거나 기존 Notebook을 재실행하지 않으며, 추천 점수·정렬 로직과 API·화면은 구현하지 않는다.

## 동일 비교 단위

세 이동수단은 동일한 출발지·목적지와 검색 시점을 기준으로 비교한다. 단위는 기존 공통 API 계약을 따른다.

| 지표 | 표준 단위 | 정렬 방향 | 비교 원칙 |
|---|---:|---|---|
| 총 이동시간 | 초 | 작을수록 우선 | 출발 준비가 끝난 검색 시점부터 목적지 도착까지의 예상 시간 |
| 예상 비용 | 원 | 작을수록 우선 | 한 번의 경로 이용에 사용자가 부담할 예상 금액 |
| 총 도보거리 | 미터 | 작을수록 우선 | 경로에 포함된 도보 구간 거리의 합 |
| 총 도보시간 | 초 | 작을수록 우선 | 경로에 포함된 도보 구간 시간의 합 |
| 접근성 상태 | 이동수단별 범주 | 필수조건/경고 | 수치 점수로 임의 환산하지 않고 이용 가능 여부와 경고로 사용 |

`total_distance_meters`는 전체 경로 거리이며 도보 부담의 우선순위 지표가 아니다. 도보 우선 비교에는 `walking_distance_meters`와 `walking_time_seconds`만 사용한다.

## 이동수단별 산정 기준

| 이동수단 | 총 이동시간 | 예상 비용 | 도보거리·도보시간 | 접근성 |
|---|---|---|---|---|
| 장애인 콜택시 | `예측 대기시간 + TMAP 차량 이동시간` | 서울 장애인 콜택시 거리요금 기준 예상값 | 승하차 지점까지의 검증된 도보 경로 데이터가 없으므로 현재 0으로 가정하지 않음 | 이용 자격·차량 유형·실제 배차 가능 여부는 현재 경로 결과만으로 판단하지 않음 |
| 지하철 | ODsay 총 이동시간 | ODsay 예상요금 | ODsay가 반환한 도보 subPath 합계. 환승역 내부 무장애 동선을 모두 포함한다고 단정하지 않음 | 출발역·모든 환승역·도착역의 엘리베이터를 핵심으로 확인하고 리프트·안전발판·장애인화장실 등은 보조 경고로 사용 |
| 저상버스 | ODsay 총 이동시간 | ODsay 예상요금 | ODsay가 반환한 출발·환승·도착 도보 subPath 합계. 실제 보행로 실측값으로 단정하지 않음 | 모든 버스 구간이 검토된 노선과 연결되고 각 구간에 `available` 노선이 있어야 함. 이는 특정 저상 차량의 도착을 보장하지 않음 |

장애인 콜택시는 예측 대기시간 모델이 아직 연결되지 않았으므로 현재 완성된 총 이동시간을 만들 수 없다. 검증된 대기시간 없이 차량 이동시간만으로 다른 수단과 시간 순위를 매기거나 고정 대기시간을 넣지 않는다. 도보값도 근거 없이 0으로 채우지 않는다.

## 추천 입력과 분석 참고 결과의 구분

### Backend Phase 7 추천 입력으로 확정

다음 값은 같은 요청에서 생성되고 공통 단위와 의미를 충족할 때만 추천 정렬 입력으로 사용한다.

| 분류 | 필드/판정 | 사용 조건 |
|---|---|---|
| 시간 | `total_time_seconds` | 콜택시는 예측 대기시간이 포함된 경우에만 사용. 지하철·버스는 외부 경로 API의 이용 가능한 결과만 사용 |
| 비용 | `total_cost_won` | 동일 검색 시점의 예상 비용이며 누락되지 않은 경우 사용 |
| 도보 | `walking_distance_meters`, `walking_time_seconds` | 둘 다 제공된 경우 사용하되 각 이동수단의 산정 한계를 warning과 함께 유지 |
| 경로 가능 여부 | `status` | `unavailable`은 수치 0으로 바꾸지 않고 추천 후보에서 제외 |
| 지하철 접근성 | 경로 내 모든 역의 접근성 lookup 결과 | 핵심 엘리베이터 조건 미충족·미확인은 경고 또는 별도 적격성 규칙으로 처리하며 임의 점수화하지 않음 |
| 저상버스 접근성 | 모든 버스 구간의 검토된 route mapping과 `accessibility_status` | `available` 노선을 선택할 수 있는 경로만 후보로 사용. `unknown`과 미매핑은 fail-closed |

시간·비용·도보의 사용자 우선순위를 적용하는 구체적인 다중 정렬 방식, 동률 처리, 접근성 경고의 후보 제외 여부는 Backend Phase 7에서 API 계약과 함께 결정한다. Analysis Phase 7은 가중치나 종합점수를 만들지 않는다.

### 표시·주의용이며 정렬값으로 직접 쓰지 않음

- 지하철의 휠체어리프트, 안전발판, 장애인화장실, 급속충전기 보유 정보
- 지하철 접근성 lookup의 기준일과 실시간 고장·점검을 반영하지 못한다는 경고
- 저상버스 노선의 저상버스 비율과 2025년 집계 기반 혼잡 위험 보조지표
- 저상버스가 특정 시간·정류장에 실제 도착하는지를 보장하지 않는다는 경고
- 외부 경로 API 도보값이 환승 내부 동선 또는 실제 보행로 전체를 보장하지 않는다는 경고

### 오프라인 분석·검증 전용

- 구·월별 장애인 지하철 승하차인원과 콜택시 출발·도착 수요의 상관·순위
- 역별 장애인 이용량 대비 접근성 시설 수와 상위 25% 시설 부담 후보
- 콜택시 시간대·요일·차량유형·이동유형별 대기시간 분포와 장시간 대기율 proxy
- 2025년 버스 승하차·추정 재차인원 기반 혼잡 hotspot

이 값들은 서로 다른 집계 단위와 모집단으로 만들어졌으므로 개별 사용자의 현재 경로를 직접 점수화하지 않는다. 모델 검증, 서비스 결과의 편향 점검, 후속 데이터 수집 우선순위 결정에만 사용한다.

### 현재 사용 금지

- 검증되지 않은 고정 콜택시 대기시간 또는 차량 이동시간만으로 만든 콜택시 총 이동시간
- 실제 콜택시 요금·승차거리처럼 검색 시점에 알 수 없는 사후 값
- 실시간으로 오인할 수 있는 2025년 지하철·버스 집계 혼잡값
- 미검증 서울 버스 실시간 도착·위치·차량유형·배차간격
- 저상버스 노선 보유 정보를 특정 저상 차량 도착 여부로 해석한 값
- 접근성 시설 개수를 임의 가중치로 합산한 종합 접근성 점수
- 누락·이용불가 값을 0으로 대체한 지표

## 기존 지하철·콜택시 비교 분석 확인 결과

기존 11번 Notebook은 2025년 1~12월, 서울 25개 구를 공통 범위로 두고 지하철 월별 집계와 콜택시 승차 완료 건을 구·월 단위로 비교했다. 지하철은 서울교통공사 관할 1~8호선의 장애인권종 승하차 집계이고 동반무임 권종이 포함될 수 있으며, 콜택시는 개별 탑승내역이다. 따라서 양쪽 수요량은 동일 모집단의 대체수요가 아니며 1:1 환산할 수 없다.

Notebook의 지역별 수요 관계, 시설 부담 후보, 혼잡·저상버스 보완 가능성 결과는 서비스 필요성을 설명하고 추천 결과를 사후 검증하는 근거로 유지한다. “지하철 접근성이 좋으면 콜택시 수요가 감소한다”와 같은 인과관계나 특정 이동수단의 자동 우선순위로 해석하지 않는다.

## 결측·이용불가·동률 처리 원칙

1. 한 지표라도 필요한 값이 없으면 0이나 평균값으로 대체하지 않는다.
2. 경로 자체가 `unavailable`이면 추천 후보에서 제외하고 사유를 보존한다.
3. 특정 우선순위 지표만 누락된 경로를 어떻게 처리할지는 Backend Phase 7 계약에서 명시하며, 분석 단계에서 임의 순위를 부여하지 않는다.
4. 값이 같은 경로의 동률 처리도 Backend Phase 7에서 안정적인 규칙으로 확정한다.
5. warnings는 수치 비교 결과와 함께 전달하며, 정렬 후 삭제하지 않는다.

## Phase 7 완료 판정

- 세 이동수단의 핵심 비교 지표를 총 이동시간·예상 비용·총 도보거리·총 도보시간·접근성 상태로 확정했다.
- 시간은 초, 거리는 미터, 비용은 원으로 통일했다.
- 이동수단별 산정 근거와 현재 데이터의 한계를 기록했다.
- 추천 정렬 입력, 표시·주의 정보, 오프라인 분석·검증 결과, 현재 사용 금지 항목을 분리했다.
- 추천 알고리즘·가중치·API·화면 구현은 Backend/Frontend 후속 Phase로 남겼다.

## 다음 Phase가 이어받을 것

1. 대기시간 모델을 검증해 `ai/` Adapter에 연결하고 콜택시 총 이동시간을 완성한다.
2. Backend Phase 7에서 사용자 우선순위, 동률, 누락 지표, 접근성 적격성에 대한 Rule-based 정렬 계약과 테스트를 구현한다.
3. 지하철 환승 내부 무장애 동선과 콜택시 승하차 접근 도보 데이터가 확보되면 도보 비교 가능 범위를 재검토한다.
4. 공식 HTTPS 기반 버스 실시간 데이터와 차량유형 코드가 검증되면 차량 단위 저상버스 접근성을 별도 Phase에서 추가한다.
