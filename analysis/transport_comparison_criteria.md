## 동일 비교 단위

세 이동수단은 동일한 출발지·목적지와 검색 시점을 기준으로 비교한다. 단위는 기존 공통 API 계약을 따른다.

| 지표 | 표준 단위 | 정렬 방향 | 비교 원칙 |
|---|---:|---|---|
| 총 이동시간 | 초 | 작을수록 우선 | 출발 준비가 끝난 검색 시점부터 목적지 도착까지의 예상 시간 |
| 예상 비용 | 원 | 작을수록 우선 | 한 번의 경로 이용에 사용자가 부담할 예상 금액 |
| 총 도보거리 | 미터 | 작을수록 우선 | 경로에 포함된 도보 구간 거리의 합 |
| 총 도보시간 | 초 | 작을수록 우선 | 경로에 포함된 도보 구간 시간의 합 |
| 접근성 상태 | `verified_available`, `verified_unavailable`, `not_verified` | 필수조건/경고 | 수치 점수로 임의 환산하지 않고 검증 상태와 경고로 사용 |

`total_distance_meters`는 전체 경로 거리이며 도보 부담의 우선순위 지표가 아니다. 도보 우선 비교에는 `walking_distance_meters`와 `walking_time_seconds`만 사용한다.

## 이동수단별 산정 기준

| 이동수단 | 총 이동시간 | 예상 비용 | 도보거리·도보시간 | 접근성 |
|---|---|---|---|---|
| 장애인 콜택시 | `예측 대기시간 + TMAP 차량 이동시간` | 서울 장애인 콜택시 거리요금 기준 예상값 | 승하차 지점까지의 검증된 도보 경로 데이터가 없으므로 `not_available`로 표현하고 현재 0으로 가정하지 않음 | 현재 `not_verified`. 이용자 자격·차량 조건·실제 배차 가능 여부를 아직 검증하지 못했다는 뜻이며 정상 접근성으로 해석하지 않음 |
| 지하철 | ODsay 총 이동시간 | ODsay 예상요금 | ODsay가 반환한 도보 subPath 합계. 환승역 내부 무장애 동선을 모두 포함한다고 단정하지 않음 | 출발역·모든 환승역·도착역의 엘리베이터를 핵심으로 확인하고 리프트·안전발판·장애인화장실 등은 보조 경고로 사용 |
| 저상버스 | ODsay 총 이동시간 | ODsay 예상요금 | ODsay가 반환한 출발·환승·도착 도보 subPath 합계. 실제 보행로 실측값으로 단정하지 않음 | 모든 버스 구간이 검토된 노선과 연결되고 각 구간에 `available` 노선이 있어야 함. 이는 특정 저상 차량의 도착을 보장하지 않음 |

장애인 콜택시는 예측 대기시간 모델이 아직 연결되지 않았으므로 현재 완성된 총 이동시간을 만들 수 없다. 검증된 대기시간 없이 차량 이동시간만으로 다른 수단과 시간 순위를 매기거나 고정 대기시간을 넣지 않는다. 도보값도 근거 없이 0으로 채우지 않는다.

`predicted_waiting_time_seconds`는 콜택시 전용 구성요소이며 세 이동수단의 공통 정렬 지표가 아니다. 콜택시 `total_time_seconds`를 산출할 때만 사용하고, 대기시간 자체를 지하철·저상버스 값과 직접 비교하지 않는다.

## 접근성 공통 상태

접근성 상태는 경로 계산 가능 여부인 `RouteResult.status`와 별개다. 경로가 계산되어도 접근성은 미확인 또는 이용 곤란일 수 있다.

| 상태 | 의미 | 추천 단계 전달 원칙 |
|---|---|---|
| `verified_available` | 현재 검토된 데이터 기준으로 이동수단별 핵심 접근성 조건을 충족 | 검증 범위와 기준일을 함께 전달 |
| `verified_unavailable` | 현재 검토된 데이터 기준으로 핵심 접근성 조건을 충족하지 못함 | 정상 접근성으로 취급하지 않고 이용 곤란 상태를 전달 |
| `not_verified` | 필요한 데이터가 없거나 일부가 미확인되어 충족 여부를 판단할 수 없음 | `verified_available`로 승격하지 않고 경고 또는 적격성 미확인 상태로 전달 |

세 이동수단의 최소 상태 예시는 다음과 같다.

| 이동수단 | 예시 상태 | 판정 근거 |
|---|---|---|
| 장애인 콜택시 | `not_verified` | 이용자 자격, 요청 시점의 실제 배차 가능 여부와 차량 조건을 현재 경로 데이터로 확인하지 못함 |
| 지하철 | `verified_available` / `verified_unavailable` / `not_verified` | 모든 이용역의 핵심 엘리베이터 조건이 확인·충족되면 available, 확인된 미충족이 있으면 unavailable, 하나라도 lookup이 미확인이면 not_verified |
| 저상버스 | `verified_available` / `verified_unavailable` / `not_verified` | 모든 구간에 검토된 `available` 노선이 있으면 available, 검토된 `unavailable`만 있으면 unavailable, 미매핑·`unknown`이 있으면 not_verified |

`not_verified`는 “문제없음”이나 “이용 가능”을 뜻하지 않는다. 구체적인 후보 제외 여부는 Backend Phase 7에서 정하되, 상태를 누락하거나 정상값으로 대체해서는 안 된다.

## 현재 `RouteResult` 계약 충돌과 후속 계약 기준

현재 `backend/app/api/contracts.py`의 `RouteResult`는 `status == available`이면 도보거리·도보시간을 포함한 모든 numeric field를 non-null로 요구한다. 따라서 검증된 도보값이 없는 콜택시는 대기시간 모델을 연결해 총 이동시간을 완성하더라도 현 계약으로는 `available` 공통 비교 결과를 만들 수 없다.

이 충돌이 해소되기 전까지 콜택시를 공통 `RouteComparisonResponse`에 억지로 넣지 않으며 도보값을 0으로 채우지 않는다. Backend Phase 7은 경로 상태와 별도로 지표별 가용 상태를 표현하도록 계약을 변경해야 한다. 최소 상태는 `available`, `not_available`이며, `not_available`인 numeric metric은 `null`이어야 한다.

후속 계약의 의미 예시는 다음과 같다. 필드의 최종 Pydantic 구조와 명칭은 Backend Phase 7에서 확정하되 아래 상태를 손실 없이 표현해야 한다.

```json
{
  "transport_type": "calltaxi",
  "status": "available",
  "total_time_seconds": 4200,
  "total_distance_meters": 12500,
  "total_cost_won": 2300,
  "walking_distance_meters": null,
  "walking_time_seconds": null,
  "metric_availability": {
    "total_time_seconds": "available",
    "total_distance_meters": "available",
    "total_cost_won": "available",
    "walking_distance_meters": "not_available",
    "walking_time_seconds": "not_available"
  },
  "accessibility_status": "not_verified",
  "warnings": [
    "콜택시 승하차 접근 도보 데이터가 없어 도보 지표를 비교할 수 없습니다.",
    "이용자 자격과 실제 배차 가능 여부가 확인되지 않았습니다."
  ]
}
```

이 예시에서 경로의 시간·비용 산출 가능성과 도보 지표 미확인은 동시에 유효하다. 도보 우선순위에서는 콜택시를 비교 대상에서 제외하고 그 이유를 표시한다. 시간 또는 비용 우선순위에서 부분 지표를 가진 경로를 후보로 유지할지와 후순위 지표 누락 처리 방식은 Backend Phase 7에서 명시적으로 결정한다.

## 추천 입력과 분석 참고 결과의 구분

### Backend Phase 7 추천 입력으로 확정

다음 값은 같은 요청에서 생성되고 공통 단위와 의미를 충족할 때만 추천 정렬 입력으로 사용한다.

| 분류 | 필드/판정 | 사용 조건 |
|---|---|---|
| 시간 | `total_time_seconds` | 콜택시는 예측 대기시간이 포함된 경우에만 사용. 지하철·버스는 외부 경로 API의 이용 가능한 결과만 사용 |
| 비용 | `total_cost_won` | 동일 검색 시점의 예상 비용이며 누락되지 않은 경우 사용 |
| 도보 | `walking_distance_meters`, `walking_time_seconds` | 둘 다 제공된 경우 사용하되 각 이동수단의 산정 한계를 warning과 함께 유지 |
| 경로 가능 여부 | `status` | `unavailable`은 수치 0으로 바꾸지 않고 추천 후보에서 제외 |
| 지표 가용 여부 | `metric_availability` | 선택한 비교 지표가 `available`인 경로끼리만 비교. `not_available`은 0으로 바꾸지 않음 |
| 콜택시 접근성 | `not_verified` | 이용 자격·실제 배차·차량 조건 미확인을 정상 접근성으로 보지 않고 명시적으로 전달 |
| 지하철 접근성 | 경로 내 모든 역의 접근성 lookup 결과 | 핵심 엘리베이터 조건 미충족·미확인은 경고 또는 별도 적격성 규칙으로 처리하며 임의 점수화하지 않음 |
| 저상버스 접근성 | 모든 버스 구간의 검토된 route mapping과 `accessibility_status` | `available` 노선을 선택할 수 있는 경로만 후보로 사용. `unknown`과 미매핑은 fail-closed |

시간·비용·도보의 사용자 우선순위를 적용하는 구체적인 다중 정렬 방식, 동률 처리, 접근성 경고의 후보 제외 여부는 Backend Phase 7에서 API 계약과 함께 결정한다. Analysis Phase 7은 가중치나 종합점수를 만들지 않는다.

### 오프라인 분석·검증 전용

- 구·월별 장애인 지하철 승하차인원과 콜택시 출발·도착 수요의 상관·순위
- 역별 장애인 이용량 대비 접근성 시설 수와 상위 25% 시설 부담 후보
- 콜택시 시간대·요일·차량유형·이동유형별 대기시간 분포와 장시간 대기율 proxy

이 값들은 서로 다른 집계 단위와 모집단으로 만들어졌으므로 개별 사용자의 현재 경로를 직접 점수화하지 않는다. 모델 검증, 서비스 결과의 편향 점검, 후속 데이터 수집 우선순위 결정에만 사용한다.

- 저상버스 노선 보유 정보를 특정 저상 차량 도착 여부로 해석한 값
- 접근성 시설 개수를 임의 가중치로 합산한 종합 접근성 점수
- 누락·이용불가 값을 0으로 대체한 지표

## 기존 지하철·콜택시 비교 분석 확인 결과

기존 11번 Notebook은 2025년 1~12월, 서울 25개 구를 공통 범위로 두고 지하철 월별 집계와 콜택시 승차 완료 건을 구·월 단위로 비교했다. 지하철은 서울교통공사 관할 1~8호선의 장애인권종 승하차 집계이고 동반무임 권종이 포함될 수 있으며, 콜택시는 개별 탑승내역이다. 따라서 양쪽 수요량은 동일 모집단의 대체수요가 아니며 1:1 환산할 수 없다.

Notebook의 지역별 수요 관계, 시설 부담 후보, 혼잡·저상버스 보완 가능성 결과는 서비스 필요성을 설명하고 추천 결과를 사후 검증하는 근거로 유지한다. “지하철 접근성이 좋으면 콜택시 수요가 감소한다”와 같은 인과관계나 특정 이동수단의 자동 우선순위로 해석하지 않는다.

## 결측·이용불가·동률 처리 원칙

1. 한 지표라도 필요한 값이 없으면 0이나 평균값으로 대체하지 않는다.
2. 경로 자체가 `unavailable`이면 추천 후보에서 제외하고 사유를 보존한다.
3. 특정 우선순위 지표가 `not_available`이면 해당 지표 비교에서 제외하고 사유를 표시한다. 다른 지표 정렬에서의 후보 유지 여부와 후순위 지표 누락 처리는 Backend Phase 7 계약에서 명시한다.
4. 현재 공통 `RouteResult` 계약이 지표별 미확인을 표현하지 못하므로, 계약 변경 전에는 콜택시를 도보값 0의 `available` 결과로 만들지 않는다.
5. 값이 같은 경로의 동률 처리도 Backend Phase 7에서 안정적인 규칙으로 확정한다.
6. warnings는 수치 비교 결과와 함께 전달하며, 정렬 후 삭제하지 않는다.

## Phase 7 완료 판정

- 세 이동수단의 핵심 비교 지표를 총 이동시간·예상 비용·총 도보거리·총 도보시간·접근성 상태로 확정했다.
- 시간은 초, 거리는 미터, 비용은 원으로 통일했다.
- 이동수단별 산정 근거와 현재 데이터의 한계를 기록했다.
- 콜택시 도보 지표 미확정과 현 `RouteResult` 계약의 충돌을 확인하고, 지표별 가용 상태를 표현할 후속 계약 기준과 유효 예시를 정의했다.
- 접근성 공통 상태와 세 이동수단별 판정 예시를 정의해 미확인을 정상 접근성으로 해석하지 못하게 했다.
- 추천 정렬 입력, 표시·주의 정보, 오프라인 분석·검증 결과, 현재 사용 금지 항목을 분리했다.
- 추천 알고리즘·가중치·API·화면 구현은 Backend/Frontend 후속 Phase로 남겼다.

## 다음 Phase가 이어받을 것

1. Backend Phase 7에서 `calltaxi available + walking metrics not_available`을 유효하게 표현하도록 공통 계약에 지표별 가용 상태와 접근성 상태를 추가한다. 이 계약 변경 없이는 콜택시 공통 비교 결과를 완성 처리하지 않는다.
2. 대기시간 모델을 검증해 `ai/` Adapter에 연결하고 콜택시 총 이동시간을 완성한다.
3. Backend Phase 7에서 사용자 우선순위, 동률, 누락 지표, 접근성 적격성에 대한 Rule-based 정렬 계약과 테스트를 구현한다. 테스트에는 콜택시 도보 미확인, 세 이동수단 접근성 상태 혼합, 선택 지표 미확인 경로 제외를 포함한다.
4. 지하철 환승 내부 무장애 동선과 콜택시 승하차 접근 도보 데이터가 확보되면 도보 비교 가능 범위를 재검토한다.
5. 공식 HTTPS 기반 버스 실시간 데이터와 차량유형 코드가 검증되면 차량 단위 저상버스 접근성을 별도 Phase에서 추가한다.
