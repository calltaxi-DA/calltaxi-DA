| 검증 항목 | 값 |
|---|---:|
| 전체 행 수 | 1,896 |
| `노선명 + 역명정규화` unique key 수 | 160 |
| 중복되는 `노선명 + 역명정규화` key 수 | 160 |

## 월별 이용량 데이터와 station accessibility master 분리

지하철 산출물은 두 성격의 데이터를 분리해서 사용한다.

| 구분 | 목적 | key | unique 조건 |
|---|---|---|---|
| 월별 이용량 데이터 | 장애인 승하차 수요 분석, 월별 추이 확인 | `사용월 + 노선명 + 역명정규화` | 월별 key로 unique |
| station accessibility master | ODsay 경로 역과 접근성 시설 연결 | `노선명 + 역명정규화` | station master에서 unique |

station accessibility master 생성 기준은 다음과 같다.

1. processed 지하철 CSV에서 접근성 시설 관련 컬럼만 분리한다.
2. `노선명 + 역명정규화` 기준으로 최신 `사용월` 1건만 선택한다.
3. 최종 master에서 `노선명 + 역명정규화` 중복이 0건인지 assertion으로 검증한다.
4. 월별 승하차 수요 컬럼(`장애인승차인원수`, `장애인하차인원수`, `장애인총승하차인원수`)은 station master의 primary 정보로 사용하지 않는다. 필요하면 별도 월별 수요 테이블에서 참조한다.

현재 processed CSV 기준으로 최신월 1건을 선택하면 station master는 160행이며, `노선명 + 역명정규화` 중복 key는 0건으로 확인된다.

## 역명·호선 Mapping 기준

### 내부 기준 key

현재 station accessibility master의 내부 canonical key는 다음이다.

```text
노선명 + 역명 정규화
```

보조 key는 다음이다.

```text
호선 + 역명 정규화
고유역번호(외부역코드)
```

`고유역번호(외부역코드)`는 서울교통공사 장애인 승하차 원본의 역 코드이므로 내부 검증에는 유용하지만, ODsay의 역 ID와 동일하다고 가정하지 않는다.

### ODsay 연결 후보 key

이번 Phase에서는 ODsay 실제 응답 샘플을 호출하지 않았으므로, 최종 ODsay mapping key를 검증 완료 상태로 확정하지 않는다. 대신 후속 ODsay 연동 Phase에서 검증할 내부 canonical key와 매핑 전략을 아래처럼 확정한다.

ODsay 지하철 경로 결과와 접근성 lookup을 연결할 때는 다음 순서를 사용한다.

| 우선순위 | key | 설명 |
|---:|---|---|
| 1 | ODsay stationID ↔ 별도 역 매핑 테이블 | 후속 API 연결 Phase에서 ODsay 응답 stationID를 확보한 뒤 검증 완료된 key로 사용 |
| 2 | `노선명 + 역명 정규화` | 현재 station accessibility master의 내부 canonical key |
| 3 | `호선 + 역명 정규화` | ODsay가 노선명을 숫자 호선으로 주는 경우 사용 |
| 4 | `역명 정규화` 단독 | 환승역·동명이역이 있어 단독 key로는 사용하지 않고 진단용으로만 사용 |

환승역은 같은 역명이라도 호선별 접근성 시설 위치가 다를 수 있으므로 역명 단독으로 합치지 않는다. 예를 들어 `서울역`, `시청`, `강남`, `신도림`처럼 여러 노선과 연결되는 역은 반드시 노선 정보를 함께 사용한다.

### 정규화 규칙

후속 ODsay 연결 Phase에서는 최소한 아래 정규화 규칙을 적용한다.

- 앞뒤 공백 제거
- 내부 공백 제거 또는 통일
- 끝의 `역` 접미사 제거 여부를 양쪽에 동일 적용
- 괄호·부역명은 원본을 보존하되 별도 정규화 컬럼에서 비교
- 노선명은 `1호선`, `2호선`처럼 processed 데이터 기준 문자열로 맞춤
- 노선명 alias는 `source_line_name → canonical_line_name` 테이블로 관리

노선명 alias 예시는 다음과 같다. 실제 alias table은 ODsay 응답 샘플을 확인한 뒤 확정한다.

| source 예시 | canonical 예시 |
|---|---|
| `수도권 1호선`, `서울 1호선`, `1` | `1호선` |
| `경의중앙선`, `경의·중앙선` | ODsay/processed 실제 표기 확인 후 확정 |
| `공항철도`, `공항철도 1호선` | ODsay/processed 실제 표기 확인 후 확정 |

정규화 결과가 여러 역에 매칭되면 자동 연결하지 않고 수동 검토 대상으로 남긴다.

## ODsay 연결 시 현재 한계

현재 저장소에는 ODsay 지하철역 stationID와 station accessibility master의 매핑 테이블이 없다. 또한 이번 Phase에서는 ODsay 샘플 응답을 호출하지 않았다. 따라서 이번 Phase의 산출물은 “ODsay 최종 key 검증 완료”가 아니라 “후속 연결을 위한 내부 canonical key와 매핑 전략 확정”이다.

따라서 `ODsay와 연결 가능`하다고 단정하지 않고, 후속 Phase에서 실제 응답 기반으로 stationID/역명/노선명 매칭 성공률을 검증해야 한다.

후속 ODsay 연동 Phase에서 해야 할 일은 다음과 같다.

- ODsay 경로 응답에서 지하철 구간별 `stationID`, 역명, 노선명을 확보
- station accessibility master와 `stationID ↔ 노선명+역명정규화` 매핑 테이블 작성
- 매핑 성공률, 미매핑 역, 다중 매칭 역을 기록
- 검토 완료된 매핑 결과만 `analysis/`에 export

## 지하철·콜택시 비교 분석 결과 활용 기준

출처: `parkchansik/11_subway_calltaxi_comparison_analysis.ipynb`

기존 비교 분석은 서울 25개 구 기준으로 진행되었다.

- 지하철 데이터: `지역명`이 서울 25개 구인 역만 사용
- 콜택시 데이터: `출발구`와 `목적구`가 모두 서울 25개 구인 이용 건만 사용
- 서울 외 지역은 분석에서 제외

확인된 데이터 규모:

| 데이터 | 원본 | 서울 기준 필터 후 |
|---|---:|---:|
| 지하철 정제 데이터 | 1,896행 | 1,788행 × 36컬럼 |
| 콜택시 정제 데이터 | 1,722,490행 | 1,588,021행 × 15컬럼 |

분석 활용 기준:

- 지하철·콜택시 비교 결과는 “서비스 추천 로직”으로 직접 사용하지 않고, 서비스 분석 근거와 검증 지표로 사용한다.
- 구별 지하철 수요와 콜택시 수요의 상관계수는 탐색 지표이며 인과관계로 해석하지 않는다.
- 지하철 접근성이 좋아도 콜택시 수요가 높은 지역은 “대체 가능성 있음”이 아니라 “추가 분석 필요 지역”으로 해석한다.
- 서울 외 지역은 현재 11번 분석에서 제외되어 있으므로, 수도권 경로 확장 시 별도 기준이 필요하다.

## 서비스 접근성 판단에 활용할 기준

지하철 경로가 ODsay에서 반환되면 접근성 평가 대상은 출발역과 도착역만이 아니라 경로에 포함된 모든 환승역까지 포함한다.

```text
접근성 평가 대상 = 출발역 + 모든 환승역 + 도착역
```

각 평가 대상 역에 대해 다음 정보를 연결한다.

| 판단 항목 | 사용할 컬럼 |
|---|---|
| 엘리베이터 이용 가능 여부 | `운행엘리베이터보유여부`, `운행엘리베이터수` |
| 엘리베이터 위치 안내 | `엘리베이터설치위치` |
| 엘리베이터 층 연결 정보 | `엘리베이터연결층` |
| 휠체어리프트 보조 정보 | `운행휠체어리프트보유여부`, `운행휠체어리프트수`, `휠체어리프트운행구간`, `휠체어리프트설치위치` |
| 승강장 간격 보조 정보 | `안전발판보유여부`, `안전발판수` |
| 장애인화장실 보조 정보 | `휠체어접근가능화장실보유여부`, `장애인화장실설치위치`, `장애인화장실층` |

1차 서비스 판단 문구는 다음처럼 단순화한다.

| 조건 | 서비스 해석 |
|---|---|
| 출발역·모든 환승역·도착역이 모두 `운행엘리베이터보유여부 = 1` | 지하철 이용 가능 후보 |
| 출발역·환승역·도착역 중 하나라도 `운행엘리베이터보유여부 = 0` | 휠체어 이용자는 주의 또는 대체수단 우선 검토 |
| 엘리베이터 상세 위치/층 정보 없음 | 접근 가능 여부는 보수적으로 안내하고 상세 정보 확인 필요 |
| 휠체어리프트만 존재 | 엘리베이터 대체 가능 여부를 단정하지 않고 보조 정보로 안내 |

주의: “엘리베이터가 있음”은 역사 내부의 모든 경로가 완전 무장애라는 뜻이 아니다. 출입구→개찰구→승강장까지 실제로 이어지는지는 엘리베이터 위치와 연결층을 함께 확인해야 한다.

특히 환승역은 단순히 역에 엘리베이터가 있다는 사실만으로 충분하지 않다. 후속 Phase에서는 가능하면 아래 동선 연결 가능성을 별도로 확인해야 한다.

```text
도착 노선 승강장 → 환승 통로/대합실 → 환승 노선 승강장
```

환승 동선 단위의 엘리베이터/리프트 연결 정보를 확보하지 못한 경우에는 “환승역 접근성 상세 확인 필요”로 보수적으로 안내한다.

`운행엘리베이터보유여부`는 원본 접근성 CSV의 기준일/운행상태를 집계한 값이다. 실시간 고장·점검 상태를 보장하지 않으므로 서비스 문구는 “접근성 데이터 기준 운행 가능한 엘리베이터 보유”처럼 표현한다.

## 이번 Phase에서 확정한 활용 대상

1. 월별 승하차 데이터와 station accessibility master를 분리한다.
2. station accessibility master의 canonical key는 `노선명 + 역명 정규화`로 둔다.
3. 현재 processed CSV 기준 `노선명 + 역명정규화`는 월별 데이터에서 중복되지만, 최신월 1건 기준 station master에서는 160개 key가 unique함을 확인했다.
4. ODsay stationID 최종 mapping key는 아직 검증 완료 상태가 아니며, 후속 API 연동 Phase에서 실제 응답 샘플로 확정한다.
5. 엘리베이터는 1차 접근성 판단의 핵심 시설로 사용한다.
6. 접근성 평가는 출발역, 모든 환승역, 도착역에 대해 수행한다.
7. 휠체어리프트, 안전발판, 장애인화장실, 급속충전기는 보조 접근성 정보로 사용한다.
8. 지하철·콜택시 비교 분석 결과는 서비스 추천 로직이 아니라 분석 근거와 검증 지표로 사용한다.
9. 서울 25개 구 기준 분석 결과와 수도권 전체 경로 추천은 범위가 다르므로 후속 확장 시 별도 기준을 둔다.

## 다음 Phase가 해야 할 일

- ODsay 지하철 경로 응답 샘플을 확보해 stationID, 역명, 노선명 필드를 확인한다.
- ODsay stationID와 station accessibility master의 `노선명+역명정규화`를 연결하는 매핑 테이블을 만든다.
- 매핑 성공률, 미매핑 역, 다중 매칭 역을 문서화한다.
- 환승 0회, 1회, 2회 경로 샘플에서 출발역·모든 환승역·도착역 접근성 lookup이 모두 검사되는지 검증한다.
- 검토 완료된 지하철 접근성 lookup만 `analysis/`에 export한다.
- backend는 `data/processed`를 직접 읽지 않고, 검토 완료된 `analysis/` 산출물만 사용한다.
