## 전처리 기준 확인

### 장애인 승하차 데이터

출처: `parkchansik/10_subway_data_preprocessing.ipynb`

- 원본: 서울교통공사 역별 월별 장애인 승하차인원 정보
- 원본 주요 컬럼: `연번`, `호선`, `고유역번호(외부역코드)`, `역명`, `승하차구분`, `수송연월`, `승하차인원수`
- 정제 기준:
  - `호선`, `고유역번호(외부역코드)`, `승하차인원수`를 숫자형으로 변환
  - `수송연월`을 `사용월`로 변환
  - `승하차구분`은 `승차`, `하차`만 허용
  - 음수 승하차인원수는 허용하지 않음
  - `사용월 × 노선명 × 역명 × 승하차구분` 중복은 허용하지 않음
  - 승차/하차 long format을 `장애인승차인원수`, `장애인하차인원수`, `장애인총승하차인원수` wide format으로 변환
  - 월별 역 단위 통계적 이상치 후보는 `이상치여부`로 표시하고, 임의 삭제하지 않음

### 콜택시 지역 기준 역 필터링

출처: `parkchansik/10_subway_data_preprocessing.ipynb`

- 콜택시 정제 파일의 `출발구`, `출발동`, `목적구`, `목적동`에 등장한 구·동을 기준으로 사용
- 행정동 경계와 지하철역 좌표를 이용해 해당 구·동에 위치한 지하철역만 선별
- 이 기준은 “콜택시 이용이 실제 발생한 생활권 주변 지하철 접근성”을 보기 위한 분석 기준이다.
- 서비스에서 모든 지하철역을 대상으로 경로를 제공하려면, 후속 export 단계에서 전체 역 기준 접근성 lookup을 별도로 만들지 여부를 결정해야 한다.

## 접근성 시설 연결 기준

현재 10번 노트북은 접근성 시설 원본을 역 단위로 집계해 processed 지하철 데이터에 결합한다.

| 시설 | 원본 key | 주요 원본 컬럼 | processed 집계 컬럼 |
|---|---|---|---|
| 엘리베이터 | `lineNm`, `stnNm` | `dtlPstn`, `bgngFlr`, `endFlr`, `oprtngSitu`, `vcntEntrcNo`, `mngNo` | `엘리베이터수`, `운행엘리베이터수`, `엘리베이터연결층`, `엘리베이터설치위치` |
| 휠체어리프트 | `lineNm`, `stnNm` | `bgngFlr`, `bgngFlrDtlPstn`, `endFlr`, `endFlrDtlPstn`, `oprtngSitu` | `휠체어리프트수`, `운행휠체어리프트수`, `휠체어리프트운행구간`, `휠체어리프트설치위치` |
| 안전발판 | `lineNm`, `stnNm` | `sftyScfldEn` | `안전발판수`, `안전발판보유여부` |
| 장애인화장실 | `lineNm`, `stnNm` | `dtlPstn`, `stnFlr`, `whlchrAcsPsbltyYn` | `장애인화장실수`, `휠체어접근가능화장실수`, `장애인화장실설치위치`, `장애인화장실층` |
| 휠체어급속충전기 | `lineNm`, `stnNm` | `stnFlr`, `dtlPstn`, `elctcFacCnt` | `휠체어급속충전기수`, `휠체어급속충전기보유여부`, `휠체어급속충전기설치위치`, `휠체어급속충전기층` |

서비스 1차 접근성 판단에서는 다음 순서를 우선한다.

1. `운행엘리베이터보유여부`
2. `운행엘리베이터수`
3. `엘리베이터연결층`
4. `엘리베이터설치위치`
5. 보조 정보: `운행휠체어리프트보유여부`, `안전발판보유여부`, `휠체어접근가능화장실보유여부`

휠체어 이용자 기준의 1차 판단에서는 에스컬레이터, 수어영상전화기, 무빙워크는 핵심 접근성 조건에서 제외한다. 현재 processed 파일에도 이 시설은 포함하지 않는다.

## 역명·호선 Mapping 기준

### 내부 기준 key

현재 processed 지하철 데이터의 내부 기준 key는 다음이다.

```text
노선명 + 역명 정규화
```

보조 key는 다음이다.

```text
호선 + 역명 정규화
고유역번호(외부역코드)
```

`고유역번호(외부역코드)`는 서울교통공사 장애인 승하차 원본의 역 코드이므로 내부 검증에는 유용하지만, ODsay의 역 ID와 동일하다고 가정하지 않는다.

### ODsay 연결 후보 key

ODsay 지하철 경로 결과와 접근성 lookup을 연결할 때는 다음 순서를 사용한다.

| 우선순위 | key | 설명 |
|---:|---|---|
| 1 | ODsay stationID ↔ 별도 역 매핑 테이블 | 후속 API 연결 Phase에서 ODsay 응답 stationID를 확보한 뒤 가장 안정적인 key로 사용 |
| 2 | `노선명 + 역명 정규화` | 현재 processed 접근성 데이터와 가장 직접적으로 맞는 key |
| 3 | `호선 + 역명 정규화` | ODsay가 노선명을 숫자 호선으로 주는 경우 사용 |
| 4 | `역명 정규화` 단독 | 환승역·동명이역이 있어 단독 key로는 사용하지 않고 진단용으로만 사용 |

환승역은 같은 역명이라도 호선별 접근성 시설 위치가 다를 수 있으므로 역명 단독으로 합치지 않는다. 예를 들어 `서울역`, `시청`, `강남`, `신도림`처럼 여러 노선과 연결되는 역은 반드시 노선 정보를 함께 사용한다.

### 정규화 규칙

후속 ODsay 연결 Phase에서는 최소한 아래 정규화 규칙을 적용한다.

- 앞뒤 공백 제거
- 내부 공백 제거 또는 통일
- 끝의 `역` 접미사 제거 여부를 양쪽에 동일 적용
- 괄호·부역명은 원본을 보존하되 별도 정규화 컬럼에서 비교
- 노선명은 `1호선`, `2호선`처럼 processed 데이터 기준 문자열로 맞춤

정규화 결과가 여러 역에 매칭되면 자동 연결하지 않고 수동 검토 대상으로 남긴다.

## ODsay 연결 시 현재 한계

현재 저장소에는 ODsay 지하철역 stationID와 processed 접근성 데이터의 매핑 테이블이 없다. 따라서 이번 Phase에서 ODsay API 연동을 구현하거나 stationID 매핑 CSV를 만들지 않는다.

후속 ODsay 연동 Phase에서 해야 할 일은 다음과 같다.

- ODsay 경로 응답에서 지하철 구간별 `stationID`, 역명, 노선명을 확보
- processed 지하철 접근성 데이터와 `stationID ↔ 노선명+역명정규화` 매핑 테이블 작성
- 매핑 성공률, 미매핑 역, 다중 매칭 역을 기록
- 검토 완료된 매핑 결과만 `analysis/`에 export

## 지하철·콜택시 비교 분석 결과 활용 기준

출처: `parkchansik/11_subway_calltaxi_comparison_analysis.ipynb`

기존 비교 분석은 서울 25개 구 기준으로 진행되었다.

- 지하철 데이터: `지역명`이 서울 25개 구인 역만 사용
- 콜택시 데이터: `출발구`와 `목적구`가 모두 서울 25개 구인 이용 건만 사용
- 서울 외 지역은 분석에서 제외

확인된 데이터 규모:

| 데이터 | 원본 | 서울 기준 필터 후 |
|---|---:|---:|
| 지하철 정제 데이터 | 1,896행 | 1,788행 × 36컬럼 |
| 콜택시 정제 데이터 | 1,722,490행 | 1,588,021행 × 15컬럼 |

분석 활용 기준:

- 지하철·콜택시 비교 결과는 “서비스 추천 로직”으로 직접 사용하지 않고, 서비스 분석 근거와 검증 지표로 사용한다.
- 구별 지하철 수요와 콜택시 수요의 상관계수는 탐색 지표이며 인과관계로 해석하지 않는다.
- 지하철 접근성이 좋아도 콜택시 수요가 높은 지역은 “대체 가능성 있음”이 아니라 “추가 분석 필요 지역”으로 해석한다.
- 서울 외 지역은 현재 11번 분석에서 제외되어 있으므로, 수도권 경로 확장 시 별도 기준이 필요하다.

## 서비스 접근성 판단에 활용할 기준

지하철 경로가 ODsay에서 반환되면 각 승하차역에 대해 다음 정보를 연결한다.

| 판단 항목 | 사용할 컬럼 |
|---|---|
| 엘리베이터 이용 가능 여부 | `운행엘리베이터보유여부`, `운행엘리베이터수` |
| 엘리베이터 위치 안내 | `엘리베이터설치위치` |
| 엘리베이터 층 연결 정보 | `엘리베이터연결층` |
| 휠체어리프트 보조 정보 | `운행휠체어리프트보유여부`, `운행휠체어리프트수`, `휠체어리프트운행구간`, `휠체어리프트설치위치` |
| 승강장 간격 보조 정보 | `안전발판보유여부`, `안전발판수` |
| 장애인화장실 보조 정보 | `휠체어접근가능화장실보유여부`, `장애인화장실설치위치`, `장애인화장실층` |

1차 서비스 판단 문구는 다음처럼 단순화한다.

| 조건 | 서비스 해석 |
|---|---|
| 승차역과 하차역 모두 `운행엘리베이터보유여부 = 1` | 지하철 이용 가능 후보 |
| 한쪽이라도 `운행엘리베이터보유여부 = 0` | 휠체어 이용자는 주의 또는 대체수단 우선 검토 |
| 엘리베이터 상세 위치/층 정보 없음 | 접근 가능 여부는 보수적으로 안내하고 상세 정보 확인 필요 |
| 휠체어리프트만 존재 | 엘리베이터 대체 가능 여부를 단정하지 않고 보조 정보로 안내 |

주의: “엘리베이터가 있음”은 역사 내부의 모든 경로가 완전 무장애라는 뜻이 아니다. 출입구→개찰구→승강장까지 실제로 이어지는지는 엘리베이터 위치와 연결층을 함께 확인해야 한다.

## 이번 Phase에서 확정한 활용 대상

1. processed 지하철 접근성 파일의 기준 key는 `노선명 + 역명 정규화`로 둔다.
2. ODsay stationID는 아직 없으므로 후속 API 연동 Phase에서 별도 매핑 테이블로 확정한다.
3. 엘리베이터는 1차 접근성 판단의 핵심 시설로 사용한다.
4. 휠체어리프트, 안전발판, 장애인화장실, 급속충전기는 보조 접근성 정보로 사용한다.
5. 지하철·콜택시 비교 분석 결과는 서비스 추천 로직이 아니라 분석 근거와 검증 지표로 사용한다.
6. 서울 25개 구 기준 분석 결과와 수도권 전체 경로 추천은 범위가 다르므로 후속 확장 시 별도 기준을 둔다.
