# 버스 추가 데이터 탐색 및 검증 기준

상태: 확정 (2026-09-12)  
목적: 저상버스 이동 추천과 혼잡도 분석에 추가로 활용할 수 있는 버스 데이터 후보를 확인하고, 현재 확보 데이터만으로 가능한 서비스 적용 범위와 후속 검증 대상을 분리한다.

## 이번 Phase 범위

이번 Phase는 **Analysis Phase 6-1**로, 현재 확보한 버스 데이터와 공식 데이터/API 후보를 확인해 “지금 사용 가능한 범위”와 “실제 API 호출 검증이 필요한 범위”를 분리한다.

원래 Phase 6의 검증 기준인 “각 버스 데이터의 확보 가능 여부와 수집 방법 확정”은 실제 API 호출, 응답 필드 의미 검증, ID mapping 검증이 필요하다. 이번 Phase에서는 그 전 단계인 후보 탐색과 서비스 적용 범위 분류까지만 완료하고, 실제 API 호출·필드 검증·수집 방법 확정은 **Analysis Phase 6-2**로 분리한다.

이번 Phase에서 하지 않는 일:

- backend API client 구현
- frontend 표시 구현
- 추천 정렬 구현
- API에서 실제 데이터를 주기적으로 수집하는 배치 구현
- 비공식 크롤러 구현
- `data/raw`, `data/processed` 재생성

서비스 코드는 `data/raw`나 `data/processed`를 직접 읽지 않고, 사람이 검토해 `analysis/`로 export한 결과 또는 backend에서 공식 API를 통해 받은 응답만 사용한다.

## 서비스 적용 범위 결정

### 지금 사용할 수 있는 것

1. 노선 단위 저상버스 접근성
   - 사용 파일: `analysis/bus/low_floor_bus_route_master.csv`
   - 사용 의미: 해당 노선에 저상버스 운행 정보가 있는지 여부
   - 제한: 특정 시간·정류장에 저상버스 차량이 도착한다는 보장은 아님

2. 시간대별·노선별 혼잡 위험
   - 사용 파일: `data/processed/bus/버스_저상노선_시간대별_추정재차인원_혼잡도_2025.csv`에서 검토 후 export된 route master 요약값
   - 사용 의미: 연간 집계 기반 혼잡 위험 보조지표
   - 제한: 실시간 재차인원이나 실제 차량 혼잡도 아님

3. 정류장/노선 수요 hotspot
   - 사용 파일: 기존 processed CSV
   - 사용 의미: 분석 근거와 추천 검증용
   - 제한: backend가 직접 읽지 않고 필요 시 `analysis/`에 별도 export해야 함

### API 검증 후 사용할 것

1. 실시간 버스 위치
   - 필요 API: 서울특별시_버스위치정보조회 서비스
   - 필요한 검증: 노선 ID, 차량 ID, 차량유형, 혼잡도 필드 의미 확인

2. 실시간 버스 도착정보
   - 필요 API: 서울특별시_버스도착정보조회 서비스
   - 필요한 검증: 정류소 ID/ARS ID와 ODsay 정류장 ID mapping

3. 차량별 저상버스 여부
   - 필요 API: 버스위치정보조회 또는 교통약자용 버스도착/위치 API
   - 필요한 검증: `busType` 또는 차량유형 코드가 저상버스 여부를 안정적으로 의미하는지 공식 코드 정의와 실제 샘플로 확인

4. 공식 재차인원/혼잡도
   - 필요 출처: 교통카드 빅데이터 시스템 또는 서울 버스위치정보 혼잡도 필드
   - 필요한 검증: 갱신주기, 호출 제한, 노선/정류장/시간대 단위, 저상버스 차량 단위 분리 가능 여부

5. 배차간격
   - 후보 1: 노선 운행정보 API에서 계획/평균 배차간격 필드 확인
   - 후보 2: 실시간 위치·도착정보에서 동일 노선 연속 차량의 도착예정시각 또는 위치 timestamp 기반 headway 계산
   - 필요한 검증: 공식 배차간격 필드 존재 여부, headway 계산에 필요한 차량 간 순서·시각 정보의 안정성

### 보류할 것

1. 비공식 크롤링
   - 공식 API와 CSV로 해결되지 않는 경우에만 검토한다.
   - robots.txt, 이용약관, 저작권, 호출 부하, 장애 대응을 확인하기 전에는 서비스 핵심 로직에 사용하지 않는다.

2. 실시간 혼잡도를 기존 2025년 추정 지표로 대체
   - 기존 지표는 혼잡 위험 비교용이지 실시간 혼잡도 표시용이 아니다.
   - 사용자에게 “현재 혼잡”처럼 표현하지 않는다.

## 추천 로직에서의 1차 사용 기준

저상버스 추천에서는 다음 순서로 데이터를 사용한다.

1. ODsay 또는 후속 버스 경로 API가 반환한 버스 노선과 `analysis/bus/low_floor_bus_route_master.csv`를 연결한다.
2. 연결된 노선의 `accessibility_status`가 `available`이면 “노선 단위 저상버스 운행 정보 있음”으로 표시한다.
3. `unavailable`이면 저상버스 대안으로 추천하지 않거나 주의 표시한다.
4. `unknown`이면 “저상버스 정보 미확인”으로 표시하고 확정 추천에 사용하지 않는다.
5. `has_top25_low_floor_congestion` 또는 p95/max 혼잡 대체지표는 “혼잡 주의” 보조 경고로만 사용한다.
6. 실시간 도착정보와 차량별 저상 여부가 검증되기 전까지 “곧 도착하는 저상버스”라고 표시하지 않는다.

## 후속 Phase가 해야 할 일

1. ODsay 인증 문제를 해결하고 버스 경로 응답에서 노선번호, `busID`, 버스 유형, 정류장 ID 필드를 확인한다.
2. 서울 버스위치정보조회 API 키를 준비하고 샘플 노선 10~20개에서 차량유형·혼잡도·저상 여부 필드를 확인한다.
3. 서울 버스도착정보조회 API에서 정류장/노선별 도착예정정보를 확보하고, ODsay 정류장 ID와 서울 BIS/ARS ID mapping 가능성을 검증한다.
4. 배차간격이 공식 필드로 제공되는지 확인하고, 없으면 실시간 위치/도착정보 기반 headway 계산 가능성을 검증한다.
5. 차량별 저상 여부가 API에서 안정적으로 확인되면 “노선 단위 접근성”과 “실시간 차량 단위 접근성”을 분리해 `analysis/`에 기준 문서를 갱신한다.
6. 공식 API로 확보되지 않는 항목은 크롤링 전에 약관·저작권·호출 제한을 검토한다.

## 최종 판단

현재 확보된 데이터만으로는 **노선 단위 저상버스 접근성**과 **2025년 집계 기반 혼잡 위험 보조지표**까지 서비스에 사용할 수 있다.

하지만 다음 항목은 아직 확정되지 않았다.

- 사용자가 기다리는 정류장에 실제로 저상버스가 도착하는지
- 차량별 저상버스 여부
- 실시간 혼잡도
- 실시간 배차간격 또는 실제 대기시간

따라서 버스 추천 MVP에서는 “노선 단위 저상버스 운행 정보 있음/없음/미확인”과 “혼잡 위험 보조 경고”까지만 사용하고, 실시간 저상버스 도착·차량별 혼잡도는 공식 API 검증 이후 확장한다.
